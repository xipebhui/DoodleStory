# Agent V1 Evaluation 计划

## 1. 目的

Evaluation 用来回答三个不同问题：

1. Agent 有没有完成用户明确要求，并只修改正确的任务、Panel 和资源？
2. 漫画创作质量是否在连贯性、角色一致性和提示词简洁度上持续改善？
3. Provider、工具、恢复和 fallback 出错时，系统是否可解释、可恢复且没有重复副作用？

首版数据集位于 `evals/agent_v1/cases.jsonl`。它是实现前的验收合同，不是当前旧 pipeline 的成绩，也不使用 Mock 结果宣称 Agent 已可用。

## 2. 三层评估

### 2.1 确定性断言

由测试代码直接判定，关键不变量要求 100% 通过：

- 资源归属和目标 Panel 正确。
- Tool 参数符合 schema，未知 Tool 不执行。
- 同一 `idempotency_key` 不产生第二张图片或第二次扣费。
- 永久错误不重试、不切换；暂时错误只按合同有界重试和切换。
- 恢复后不重放已经成功的副作用。
- 取消后不保存返回图片、不扣费、不复活 Run。
- 模型结构化输出字段和类型校验通过；仅“合法 JSON”不算成功。
- 对话重开后能从数据库恢复，而不是依赖原浏览器连接或单一 Provider 的 response ID。

### 2.2 创作质量评分

由固定评分 rubric 进行人工或独立 Judge 评分，每项 1 到 5 分：

| 维度 | 5 分含义 | 1 分含义 |
| --- | --- | --- |
| 目标遵循 | 所有显式约束均落实且无越权改动 | 忽略关键要求或擅自改变目标 |
| 叙事连贯 | 相邻 Panel 因果、人物状态和节奏连续 | Panel 像相互独立的随机画面 |
| 角色一致 | 身份锚点、年龄阶段、服装关系稳定 | 同一角色频繁变脸或关系错乱 |
| 画面可执行 | 每格目标清楚、构图充分且无矛盾 | 描述抽象、冲突或无法生图 |
| Prompt 简洁 | 只保留当前图必要约束，无重复堆叠 | 冗长拼接、相互冲突、重复强调 |
| 修改局部性 | 只影响用户指定对象并保持其余上下文 | 修改一个 Panel 却重写整个任务 |

初始开发门槛：核心用例每个维度不得低于 3 分，全部质量评分平均不低于 4 分。Judge prompt、模型和 rubric 版本必须随结果记录，不能只保存总分。

### 2.3 运行指标

每次 Eval Run 记录：

- 场景完成率和首次完成率。
- 模型调用、Tool 调用、图片调用次数。
- 主平台重试次数、fallback 次数和原因。
- 每步与整轮延迟、token usage 和图片成本。
- schema 校验失败、重复 Tool Call、恢复次数和人工介入次数。
- Run 最终状态及用户可见错误是否与内部错误分类一致。

性能指标先建立基线，不在没有真实运行样本时虚构阈值。积累至少 30 次本地 Eval Run 后，再按分位数制定延迟和调用次数门槛。

## 3. 执行层级

### PR 快速集

- 纯确定性单测。
- Provider Router 故障注入。
- 不真正调用图片平台的 Tool schema、权限、幂等和状态机测试。

### 本地真实模型集

- 使用火苗主平台运行所有创作与结构化用例。
- 对 Router 用例显式注入主平台临时错误，验证切到 LIO 后仍能读取完整应用侧上下文。
- 对需要图片判断的用例使用真实生图/VL 调用并记录资产 ID；未配置时明确标记 `not_run`，不能填充占位成绩。

### 发布前回归集

- 固定数据集版本、模型名、风格快照和 Judge 版本。
- 与上一个可接受基线逐项比较退化，而不是只看新的平均分。
- 所有关键确定性不变量 100% 通过；任何重复扣费、跨用户资源访问、错误 Panel 修改或取消后保存结果都直接阻止发布。

## 4. 可观测性要求

一个 Eval case 必须能通过 `case_id -> conversation_id -> run_id -> step_id -> task/panel/image_version_id` 追到所有事实。每个模型步骤还要包含 `provider`、`model`、`api_shape`、`attempt`、`fallback_from`、`fallback_reason`、延迟、usage、Provider request ID 和脱敏错误。

不记录 Chain of Thought。保存用户可见回答、规范化模型输入输出项、Tool Call/Output、结构校验结果和状态转换即可复盘。

## 5. 数据集维护规则

- 修复线上真实问题时，先新增一个能复现问题的 case，再修改实现。
- 用例 ID 和既有期望不可静默改写；需求变化时升级数据集版本并说明原因。
- 不把当前模型偶然输出的完整文本固化为唯一答案，优先断言业务不变量。
- 风格、角色、任务、Panel 和图片引用使用稳定测试 fixture ID，不使用展示名称作为事实 ID。
- 质量评估必须保留逐维理由；Judge 与被测 Agent 不共享隐藏状态。

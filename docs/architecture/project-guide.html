01 · Mental model

一句话理解：这是一个“持久化 Agent 编排层”，外接内容与媒体工具。

用户在 React 工作台提交目标。FastAPI 先把会话、Run、Skill 版本与资源引用写入数据库；单实例的进程内 Worker 再运行 Native Agent。模型只决定下一步意图，真正产生图片、语音、字幕、视频、研究结果或发布动作的是受控 Function Tool。每个关键步骤、产物、审批与事件会回写数据库，再通过 SSE 投影到界面。

这正是可扩展点：新 Agent 不该从“再接一个模型”开始，而应从“定义一个固定版本的 Skill、可审计的 Tool、副作用前的 Gate、可恢复的 Artifact”开始。

02 · System map

系统由五层组成：界面、应用、Agent、权威状态、外部工具。

已可复用

Native Agent 基座

Run、Skill Version 快照、Step、Artifact、Approval、事件、取消和启动恢复已经在当前架构内；新流程可接入这些统一语义。

有条件可用

外部 Provider

模型、图片、存储、研究和发布服务依赖环境配置、账号和可用性。Tool 存在不等于 Provider 已为新赛道做好配置。

不应假设已具备

分布式调度与赛道策略

当前 Worker 是单实例进程内队列；赛道发现、策略评分、批量实验、数据回流不是一个已完成的通用工作流。

03 · Agent lifecycle

一次 Agent Run 为什么能等待、恢复和追踪？

关键不是对话本身，而是先把执行事实写入权威状态：输入、Skill 版本、资源、模型请求、Tool Effect、产物、审批和事件都有对应的记录。模型重试或刷新页面不应凭前端猜测继续执行。

A. 固定输入

创建 Run

会话、Skill Version、用户资源和上下文快照先入库。

B. 受控执行

Worker 调度

进程内队列启动合法 Run，持久化当前状态与 Checkpoint。

C. 模型决策

Agent Loop

Responses 模型选择下一步，Function Tool 有明确白名单。

D. 副作用留痕

Tool 与 Artifact

以 Tool Call ID 做幂等；成功、失败、资产和事件均回写。

E. 人在回路

Gate / 终态

发布或高成本动作需要批准；SSE 只展示后端权威投影。

04 · YouTube today

研究、制作、发布已经有连接点，但不是一条自动赛道流水线。

目前的研究 Tool 能读取频道洞察；账号上下文 Tool 能提供频道定位、对标账号和近期视频；媒体 Tool 能产出图片、旁白、字幕和 Remotion 视频；发布 Tool 在明确确认后会调用外部视频平台创建异步上传任务。这些是构建新赛道 Agent 的原材料。

为什么要强调“不是 DoodleStory 直连 YouTube”？
频道研究由同级多平台导入服务处理，DoodleStory 当前请求的是它的 /api/v1/youtube/channel-insights；视频发布由 video.inboxlinks.top 的 YouTube 上传任务 API 承担。新流程设计时应分别给研究失败、媒体失败和远程发布任务轮询定义状态，不要把它们归为同一个 Provider 错误。

06 · Blueprint

把“研究一个新的 YouTube 赛道”落成 Agent 的最小切面。

建议先做一个小而可验证的 Sprint，而不是一次性做“全自动频道”。例如：给定 3–10 个对标频道，产出一份可追溯的赛道研究报告和 3 个待确认选题；确认后才进入脚本与视频制作。这个切面能够真实验证研究 Tool、策略 Artifact、Gate 和后续媒体链的交接。

  1. 先写业务合同，而不是 Prompt。写清输入的频道数量、研究问题、允许使用的数据、报告结构、人工确认点、失败的可见结果和成本上限。这个合同应成为新 Sprint 的验收标准。
  2. 把赛道规则封装为新 Skill。Skill 只描述该赛道的目标、方法、输出格式与允许的 Tool；启用后版本固定到 Run，避免用户中途改规则影响正在执行的研究。
  3. 只新增必要的原子 Tool。优先复用频道研究、账号上下文和媒体 Tool。若需要搜索、指标读取或素材分析，再各自新增一个明确输入 / 输出 / 幂等边界的 Tool，而不是让模型绕过后端直接请求外部服务。
  4. 把中间结论变成 Artifact 和 Gate。研究报告、赛道策略、选题列表、脚本、视觉方案和可发布视频都应可追溯。成本高、会公开发布或会改变方向的动作前设置明确 Gate。
  5. 接入现有控制与事件面。API 使用 owner 校验和 state_version；前端从 SSE 投影读取状态。支持取消、刷新、恢复和远程 Tool 不确定结果，不另造一套状态机。
  6. 用一条真实链路验收。选一个具体赛道，从对标频道研究到一支审核通过的视频；记录 Run、Artifact、Gate、媒体资产和发布任务 ID，再把真实缺口写入 QA。
推荐第一 Sprint：“对标频道 → 赛道报告 → 3 个选题 → 人工确认”。这条链只需要复用已有研究能力和 Agent 持久化，不会在研究阶段就产生媒体成本或发布副作用。

07 · Decisions and boundaries

几个最容易误判的边界。

SiliconFlow 不是 Agent 主模型地址

Native Agent 当前使用 TEXT_FALLBACK_BASE_URL 的 Responses API；SiliconFlow 负责独立的 chat.completions、多模态和语音链路。允许模型名单也不等于每项能力都已接入。

发布必须是显式外部副作用

当前 publish_youtube_video 只有在频道、可发布视频与明确确认均具备时才暴露。新流程不能把“生成成功”误当作“允许发布”。

当前队列不是分布式基础设施

进程内 asyncio.Queue 配合单实例锁适合当前规模和恢复语义。跨机器、高并发、定时批量生产要单独讨论，不应静默当作已有能力。

传统任务链路、早期 Agent 与 Native / Durable Runtime 如何看？
仓库中仍保留传统图文 / 视频任务和早期 Agent 实体与服务，它们对既有功能有价值。新 Agent 流程应优先接入当前的 Native / Durable Runtime：它具备 Skill Version 固定、Tool Effect、Gate、控制命令、恢复和 SSE 投影。不要因为旧代码仍在仓库，就把它当成新能力的默认落点。

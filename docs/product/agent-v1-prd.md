# DoodleStory Agent V1 精简 PRD

## 1. 文档目的

本文定义 DoodleStory 从固定生成 Pipeline 迁移到 Agent 驱动创作后的第一版产品行为。它用于约束后续后端、数据库、前端和 Evaluation，不代表当前功能已经实现。

Agent V1 的重点不是“在旧流程外包一层聊天框”，而是让漫画导演 Agent 根据对话上下文决定故事方向、分镜、图片提示词、图片检查和局部重试。代码仍负责权限、状态、幂等、积分、存储和失败边界，但不再用一组固定 Prompt 串联所有创作决定。

## 2. 要解决的问题

当前固定 Pipeline 存在四个核心问题：

1. 故事设计、分镜和生图提示词由互相隔离的单次模型调用完成，缺少持续上下文。
2. 最终生图提示词叠加过多模板和硬规则，模型执行效果不稳定。
3. 代码中存在较多字符串拼接和固定分支，创作要求变化时需要继续增加硬逻辑。
4. Provider 失败、输出校验和图片重试散落在业务流程中，难以观察和统一控制。

## 3. V1 产品目标

- 用户可以从一个 idea、完整故事或参考作品开始对话。
- Agent 可以在同一个上下文中完成故事方向、角色、分镜和图片生成决策。
- 漫画任务作为对话中的持续对象存在，用户离开页面后仍可继续运行。
- 用户重新进入历史对话时，可以看到消息和任务的最新状态。
- 用户可以引用风格、固定角色、历史任务、Panel 和图片版本。
- 用户可以说“重试第 4 张”或“恢复上一版”，系统能确定目标对象。
- 每次模型调用、工具调用、Provider 切换和图片版本变化都可追踪、可评估。

## 4. 非目标

- 第一版不做多 Agent 团队、Agent handoff 或用户可配置工作流。
- 不使用无限画布或节点编排器。
- 不要求 Agent 直接操作数据库、积分或文件系统。
- 不把模型隐藏推理过程展示给用户。
- 不在本阶段替换现有正式任务页面和生成链路。
- 不引入 LangChain、LangGraph 或外部持久化工作流引擎。

## 5. 核心概念

### 5.1 Conversation

用户可重新进入的长期对话容器。一个 Conversation 保存消息、资源引用和关联漫画任务，但不等于一次模型调用。

### 5.2 Turn

一次用户输入以及由它触发的 Agent 处理。用户发送一条新消息时创建一个 Turn。

### 5.3 Agent Run

Agent 对一个 Turn 的实际执行。一个 Run 可以包含多次模型调用、图片生成和 VL 检查，也可以暂停等待用户或外部图片任务。

### 5.4 Comic Task

对话中创建的漫画作品任务。一个 Conversation 可以先讨论而没有任务，也可以包含多个任务或同一任务的多轮修改。

### 5.5 Panel 与 Image Version

Panel 是漫画中有明确顺序的画面单元。每次生成或修改产生新的 Image Version；旧成功版本必须保留，切换当前版本需要显式操作。

### 5.6 Resource Reference

用户通过 `@` 明确选中的风格、角色、任务、Panel 或图片版本。引用必须保存稳定资源 ID 和当次展示名称，不能只把名称拼进纯文本。

## 6. 核心用户流程

### 6.1 从 idea 创建漫画

1. 用户新建对话并输入 idea。
2. Agent 判断信息是否足够；信息不足时只询问会显著改变作品的关键问题。
3. Agent 形成故事方向和分镜计划，并在对话中创建 Comic Task。
4. Agent 根据计划调用图片生成和 VL 检查能力。
5. 任务卡片持续更新 Panel 进度；用户离开对话不取消 Run。
6. 完成后 Agent 总结结果和仍需用户决定的问题。

### 6.2 从参考作品改编

1. 用户提供抖音链接、已有内容提取记录或历史任务。
2. Runtime 把已授权资源解析为结构化上下文。
3. Agent 提炼可借鉴的叙事机制，不能默认逐页照搬原作品。
4. Agent 给出改编方向；涉及主题、人物关系或结局的重大改变时可以等待用户确认。
5. 用户确认后进入漫画任务生成。

### 6.3 修改指定 Panel

1. 用户在任务详情选择 Panel 或通过 `@Panel` 引用目标。
2. 用户描述修改方向。
3. Agent 读取该 Panel 的剧情目标、当前图片、角色/风格约束和历史检查结论。
4. Agent 只对目标 Panel 生成新版本，不修改其他已接受 Panel。
5. 新版本通过 VL 检查后成为候选；是否自动设为当前版本由任务策略决定并在界面明确显示。

### 6.4 继续历史对话

1. 用户从历史列表进入 Conversation。
2. 页面加载持久化消息、资源引用和任务最新状态。
3. 如果 Run 正在执行，展示当前公开步骤；如果正在等待用户，展示需要决定的问题。
4. 用户可以继续发送消息，不需要保持原浏览器连接。

## 7. Agent 与系统的责任边界

### Agent 决定

- 是否需要向用户追问。
- 故事主题、情绪推进、角色关系和分镜方案。
- 每个 Panel 的画面目标和简洁图片 Prompt。
- 什么时候调用生图或 VL 检查。
- 检查失败后是修改 Prompt、重新生成还是请求用户决定。

### Runtime 强制保证

- 用户权限和资源归属。
- Conversation、Run、Step、Tool Call 和任务状态持久化。
- Tool 参数结构校验。
- Provider 路由、超时、有界重试和失败分类；熔断只在真实运行数据证明需要后评审。
- 图片生成积分占用、成功扣费和失败释放。
- Tool 幂等、任务取消和服务重启恢复。
- 最大 Turn、模型调用、图片调用和费用边界。
- 用户可见事件不包含模型隐藏推理。

## 8. 功能要求

### 8.1 对话

- 支持新建、搜索、进入和继续历史对话。
- Conversation 标题可以由首轮内容生成，但用户输入必须原样保存。
- 消息支持用户、Agent、任务卡片和用户可见事件四类展示。
- 发送消息后页面断开，不应丢失已创建的 Run。

### 8.2 资源引用

- `@风格`、`@角色`、`@任务`、`@Panel` 和 `@图片版本` 保存结构化引用。
- Runtime 在每轮开始时解析引用并校验权限。
- 已删除或无权限资源必须明确提示，不能只丢掉该上下文继续生成。
- 历史任务优先读取任务快照，不受风格或角色资源后续编辑影响。

### 8.3 任务与进度

- Agent 创建任务后，任务卡片出现在所属对话中。
- 任务状态至少区分：`queued`、`running`、`waiting_for_input`、`paused`、`succeeded`、`failed`、`cancel_requested`、`cancelled`。
- 任务卡片展示已完成 Panel 数、总数、当前公开步骤和失败信息。
- 任务离开当前页面后继续执行；重开 Conversation 时显示数据库中的最新状态。

### 8.4 Panel 版本

- 修改指定 Panel 时必须产生新版本，不能覆盖旧成功图片。
- 每个版本保存生成 Prompt、Provider、模型、工具调用、检查结果和创建时间。
- “恢复上一版”是显式切换当前版本，不重新调用图片 Provider。
- 同一修改指令重试时必须通过幂等机制避免重复扣费或重复创建相同 job。

### 8.5 暂停、继续和失败

- 暂停发生在 Step 安全边界，不强行终止已经发出的同步 Provider HTTP 请求。
- Provider 返回后如果任务已取消，结果不得保存为成功资产或扣费。
- Run 失败时展示用户安全错误；内部错误、Provider request ID 和原始追踪只在调试信息中保存。
- 自动重试和 Provider fallback 必须记录，不允许静默发生。

## 9. 非功能要求

- 数据库是对话、Run、Step、Tool Call 和任务状态的事实来源。
- 第一版继续使用进程内队列调度，队列中只传稳定 ID。
- 服务启动时扫描并恢复可以安全重放的 Run。
- 所有外部副作用必须有幂等键。
- 每个 Run 必须可以按 `conversation_id`、`turn_id`、`run_id`、`tool_call_id` 和关联任务 ID 检索。
- Provider 主备切换不得依赖只在某个平台有效的远程 response ID。
- 第一版可以先流式展示应用级状态，不要求转发模型 Token 流。

## 10. V1 验收场景

1. 用户新建对话，从一句 idea 创建五格漫画任务。
2. 用户离开并重新进入，对话和任务进度仍然存在。
3. 用户引用保存的风格和固定角色创建任务。
4. 用户引用 Panel 3，只修改表情并保留构图、服装和其他 Panel。
5. 用户恢复 Panel 3 的旧成功版本，不产生新的图片费用。
6. 火苗发生可重试故障时切换 LIO，并在运行记录中可见。
7. 两个平台都失败时 Run 明确失败，不返回占位结果。
8. 服务在图片工具执行结束后的 checkpoint 重启，可以从下一安全步骤恢复。
9. 相同 Tool Call 被重复投递时不重复创建图片 job 或扣费。
10. Evaluation 可以从保存的 Run、Step、Tool Call 和任务产物重放评分。

## 11. 上线前仍需确认

- 火苗和 LIO 的 `gpt-5.6-terra` 是否都能通过 OpenAI Agents SDK 的 Responses Function Calling、Tool Output 和应用侧完整输入重放；该结果决定正式 API shape。
- 第一版新版本通过 VL 检查后是自动成为当前版本，还是等待用户接受。
- Agent 每个 Run 的默认最大模型调用数、生图次数和费用上限。

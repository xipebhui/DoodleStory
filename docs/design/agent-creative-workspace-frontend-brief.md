# DoodleStory Agent 漫画创作工作台前端设计 Brief

## 如何使用本文档

将本文档完整交给负责前端设计或实现的 AI，并附上下面这句话：

> 请基于本文档直接实现一个可运行、可点击的高保真前端原型。不要先复述需求，不要制作营销落地页，不要把它设计成工作流搭建器。使用本地演示数据完成文档规定的核心交互，不需要接真实后端。

本文档用于让多个设计方案在相同产品目标和演示任务下独立发挥。以下内容分为两类：

- `必须满足`：产品语义、核心页面区域、交互路径、演示内容和状态表达。
- `允许发挥`：具体排版、色彩细节、字体、微动效、组件形态和空间比例。

不要为了追求差异而改写产品目标。

## 1. 产品背景

DoodleStory 是一个把 idea、故事文本或参考作品创作成连续漫画图片的产品。

新版本不再以“填写表单并提交固定 Pipeline”为核心，而是由一个持续理解上下文的漫画导演 Agent 完成创作。Agent 会根据用户目标自主规划故事、角色、分镜和生图提示词，调用生图与视觉理解工具，查看生成结果，并根据质量决定接受、修改或重新生成。

用户会通过自然语言持续参与，例如：

- “把这个 idea 做成五格漫画。”
- “主角使用我保存的角色林夏。”
- “第 3 张表情更紧张，衣服和场景不要变。”
- “这个版本不如上一版，恢复 v1。”
- “结尾换成雨停后的清晨。”

这个产品首先是创作工具，其次才是任务监控工具。

## 2. 设计任务

设计一个桌面端优先的 Agent 漫画创作工作台，让用户在同一个页面中完成：

1. 与 Agent 对话。
2. 理解 Agent 当前正在做什么。
3. 查看当前故事、风格和角色资源。
4. 按顺序查看整组漫画分镜。
5. 选中某个 Panel 或图片版本，并围绕该对象继续对话。
6. 查看图片版本、视觉检查结果和生成状态。
7. 接受、重试、恢复或继续修改一张图片。

设计应体现“人和 Agent 在同一张数字分镜桌上共同工作”，而不是“用户向黑盒提交任务”。

## 3. 核心设计意图

### 3.1 Visual thesis

一张安静、专注、具有编辑感的数字分镜桌：界面保持克制，生成图片是最强视觉元素，状态和控制清晰但不抢画面。

推荐延续 DoodleStory 当前深色工作台的品牌基础：接近墨黑的背景、层次清晰的中性表面、偏白正文和一个暖色强调色。允许设计者提出更好的单一视觉方向，但不得使用多色渐变、霓虹科技装饰或通用 SaaS 仪表盘风格。

### 3.2 Content plan

首屏只承担四个任务：

1. 告诉用户当前在哪个漫画项目中。
2. 告诉用户 Agent 当前状态。
3. 让整组分镜成为视觉中心。
4. 让用户能够选中对象并立即继续对话。

不设置营销 Hero、数据统计卡片、教程 Banner 或大段产品说明。

### 3.3 Interaction thesis

通过三种交互让工作台有“共同创作”的感觉：

1. 画布选择与对话上下文联动：点击 Panel 或版本后，对话输入区立即出现对应上下文标签。
2. Agent 状态在原位变化：正在规划、生成、检查和完成的状态出现在对应 Panel 上，不依赖全屏遮罩。
3. 新图片版本以短促、克制的过渡进入当前 Panel，旧版本仍能被查看和恢复。

## 4. 与当前产品交互的区别

当前产品是：

```text
创建任务表单 → 任务列表 → 任务详情抽屉 → 分镜卡片 → 单卡修改
```

目标工作台是：

```text
进入漫画项目 → 与 Agent 对话 → 画布实时出现创作结果
                    ↕
             选择对象并继续修改
```

必须消除以下体验：

- 用户在开始创作前必须填写一大组模式和选项。
- 分镜只在很深的详情抽屉中出现。
- 每个 Panel 下方都堆叠 Prompt、调试信息、版本列表和修改文本框。
- 用户说“修改第三张”时，系统只能从纯文本猜测目标。
- Agent 的中间行动只表现为一个笼统的加载状态。

## 5. 画布边界

第一版采用“结构化分镜画布”，不是无限画布。

必须满足：

- Panel 有明确顺序。
- 用户能快速浏览整组漫画。
- Panel 可以被选中。
- 当前选中对象清晰可见。
- 画布允许横向浏览或自适应网格布局。
- 画布可以容纳生成中、检查中、已接受、需要处理等状态。

第一版不要实现：

- 无限缩放和平移。
- 任意节点连线。
- 用户搭建 Agent 工作流。
- 自由坐标和复杂自动布局。
- 把工具调用过程画成流程图。
- 类似视频剪辑器的多轨时间线。

用户创作的是漫画，不是在编辑 Agent 执行图。

## 6. 页面信息架构

### 6.1 顶部项目栏

必须包含：

- 返回项目列表。
- 项目标题。
- 当前项目状态，例如 `Agent 正在检查 Panel 4`。
- 一个克制的全局操作区，例如暂停、继续或导出。

项目栏不承担全站完整导航。工作台需要尽可能保留横向空间。

### 6.2 Agent 对话区

主要职责：

- 展示用户消息和 Agent 回应。
- 展示 Agent 可理解的简短行动记录。
- 输入自然语言。
- 携带 `@风格`、`@角色`、`@Panel`、`@图片版本` 等上下文引用。

行动记录使用用户能理解的语言：

- `已整理故事方向`
- `正在生成 Panel 4`
- `Panel 4 人物外观检查通过`
- `Panel 3 的表情不符合剧情，准备生成新版本`

不要显示：

- 模型隐藏思维过程。
- 大段 JSON。
- 完整系统 Prompt。
- 无意义的“调用工具成功”。

对话输入区必须持续可见。选中画布对象后，输入区显示可移除的上下文标签，例如：

```text
[@Panel 3] [@当前图片 v2]
人物表情再紧张一点，其他都不要变……
```

### 6.3 中央创作画布

这是页面视觉中心，生成图片必须占据主要面积。

画布顶部或边缘需要以紧凑方式展示当前创作上下文：

- 故事概要。
- 当前风格。
- 主要角色。

这些资源不应变成一排大型 Dashboard 卡片。使用简短标签、头像、缩略图、可展开摘要或其他克制方式。

画布主体按顺序展示 Panel：

- Panel 编号。
- 当前图片或稳定占位。
- 一句话剧情目标。
- 当前状态。
- 当前版本号。
- 被选中时的明确反馈。

图片之间应具有连续作品的感觉，而不是互不相关的素材库。

### 6.4 对象检查器

检查器只展示当前选中对象的详细信息，避免把细节堆在每张 Panel 卡片下面。

选中 Panel 时可展示：

- 剧情目标。
- 当前图片。
- Agent 的最新视觉检查结论。
- 当前版本和历史版本。
- `重新生成`、`接受当前版本`、`恢复上一版` 等动作。

选中角色时可展示：

- 角色名和参考图。
- 简短身份锚点。
- 出现在哪些 Panel。

选中风格时可展示：

- 风格名称和参考图。
- 简短风格描述。

Prompt、模型线路、Provider Request ID 等调试信息可以放在二级折叠区，不得占据检查器第一视觉层。

### 6.5 运行状态

页面必须让用户看懂 Agent 是：

- 空闲。
- 正在思考下一步。
- 正在调用文本模型。
- 正在生成图片。
- 正在用 VL 检查图片。
- 等待用户决定。
- 已暂停。
- 失败。

状态不能只使用颜色表达，需要搭配文字、图标或动效。

## 7. 推荐桌面布局

下面只是功能分区，不是要求逐像素照抄：

```text
┌─────────────────────────────────────────────────────────────────────┐
│ ← 项目   被裁员的第七天        Agent 正在检查 Panel 4    暂停  导出 │
├──────────────────┬───────────────────────────────┬──────────────────┤
│                  │ 故事 / 风格 / 角色摘要         │                  │
│ Agent 对话       │                               │ 当前对象检查器   │
│                  │ 分镜画布                       │                  │
│ 用户消息         │                               │ 当前图片         │
│ Agent 回应       │  [01] [02] [03] [04] [05]    │ 质量检查         │
│ 行动记录         │   ✓    ✓   选中  检查中  待生成 │ 版本历史         │
│                  │                               │ 对象操作         │
│ @上下文输入      │                               │                  │
├──────────────────┴───────────────────────────────┴──────────────────┤
│ 本轮：已完成 3/5 张 · 已使用 2 次生图 · 当前等待 Panel 4 检查结果    │
└─────────────────────────────────────────────────────────────────────┘
```

建议在 1440×900 桌面视口中完整表现主要工作区，不依赖浏览器整体纵向滚动。各区域可以独立滚动。

允许设计者调整左右区域位置和宽度，但必须保持：图片是主角、对话随时可用、选中对象详情明确。

## 8. 固定演示项目

所有对比原型使用同一项目，避免演示内容差异影响判断。

### 项目信息

- 项目名：`被裁员的第七天，我开始在街角画画`
- 创作形式：5 张连续漫画
- 风格：`暖灰铅笔电影感`
- 主角：`林夏，29 岁，黑色短发，深绿色外套`
- 辅助角色：`阿布，橘白流浪猫`

### 故事概要

林夏被裁员后连续一周不敢告诉家人。她每天假装上班，却坐在街角给路人画速写。第七天，一只流浪猫一直守在她身边。有人把她画画的视频发到网上，傍晚时她收到第一笔真正属于自己的订单。

### 五个 Panel

1. `早高峰，林夏背着电脑包逆着人群走出地铁，神情疲惫。`
2. `她坐在街角展开速写本，身旁放着没有打开的电脑。`
3. `林夏收到家人询问工作是否顺利的消息，强忍情绪，橘白猫靠近她。`
4. `陌生女孩蹲在旁边看她画画，悄悄举起手机记录。`
5. `雨停后的傍晚，林夏收到第一笔头像订单，橘白猫趴在她脚边。`

### 初始状态

- Panel 1：`已接受 · v1`
- Panel 2：`已接受 · v1`
- Panel 3：`已生成 · v2 · 当前选中`
- Panel 4：`VL 检查中 · v1`
- Panel 5：`等待生成`

### Panel 3 检查结果

```text
人物与参考角色一致，服装和场景连续性正常；但表情过于平静，没有表现出收到家人消息时的紧张和愧疚。
```

### Panel 3 版本

- v1：表情明显悲伤，画面过于煽情。
- v2：构图和角色一致性更好，但表情过于平静。
- v3：由演示交互生成的新版本。

## 9. 必须完成的演示交互

原型不需要接真实后端，但以下交互必须真实可点击、状态可见，不能只做静态截图。

### 交互 A：选择对象

1. 初始选中 Panel 3。
2. 点击 Panel 1，画布选择态移动到 Panel 1。
3. 对象检查器切换为 Panel 1 内容。
4. 对话输入区出现 `@Panel 1` 上下文标签。
5. 再点击 Panel 3，恢复 Panel 3 上下文。

### 交互 B：通过对话修改 Panel 3

1. 输入或点击示例指令：`人物表情再紧张一点，衣服、构图和场景保持不变。`
2. 用户消息进入对话。
3. Agent 展示简短回应：`我只调整林夏的表情，保留当前构图、服装和雨天街角。`
4. Panel 3 原位依次显示：`修改提示词` → `生成中` → `检查中` → `新版本完成`。
5. 生成完成后出现 v3，并成为当前版本。
6. 检查器版本历史中仍能看到 v1 和 v2。

演示可以用定时器模拟过程，但状态顺序必须清楚，且不能伪装成真实后端结果。

### 交互 C：切换和恢复版本

1. 在检查器中查看 v1、v2、v3。
2. 点击某个版本后预览发生变化。
3. 历史版本与当前版本必须有明确区分。
4. `恢复为当前版本`需要显式操作，不得点击缩略图后立即覆盖当前版本。

### 交互 D：暂停和继续

1. 顶部点击`暂停`后，Panel 4 停留在当前状态。
2. 全局状态显示`已暂停`。
3. 点击`继续`后恢复运行态。

## 10. 视觉与组件约束

### 必须满足

- 生成图片是界面最突出的视觉内容。
- 使用清晰排版和空间层级，不依赖厚重阴影。
- 不把每块内容都放进卡片。
- 重复 Panel 可以使用卡片，因为图片和选择操作就是卡片本身的语义。
- 全局只使用一个主要强调色。
- 状态、错误、选择和禁用态都必须可辨认。
- 中文文字不能拥挤、截断或与按钮重叠。
- 支持键盘聚焦态，按钮有明确名称。
- 画布、对话和检查器使用分隔和表面层级，而不是三层厚重外框。

### 避免

- 通用 Dashboard 卡片矩阵。
- 紫蓝渐变和发光边框堆叠。
- 大面积装饰性玻璃拟态。
- 每个状态都使用不同鲜艳颜色。
- 大量圆角胶囊和徽标。
- 在首屏直接展示完整 Prompt。
- 让 Agent 消息气泡占据大部分页面。
- 让检查器比生成图片更抢眼。
- 使用没有叙事关系的随机图库图片。

## 11. 动效建议

至少实现两种有意义的动效：

1. 画布选择变化：Panel 选择、检查器内容和对话上下文同步过渡。
2. Agent 生成状态：同一 Panel 内从准备、生成、检查到完成，不跳动整体布局。
3. 新版本出现：当前图片平滑替换，版本历史增加一项。

动效应短促、稳定并尊重 `prefers-reduced-motion`。不要加入持续漂浮、装饰粒子或与操作无关的循环动画。

## 12. 响应式要求

本次评审以桌面端为主。

最低要求：

- 1440×900：三块工作区同时可用。
- 1280×800：不遮挡核心操作，允许压缩检查器宽度。
- 小于 900px：允许把检查器变成抽屉，把对话和画布切换为主从视图。

不要求为手机完成所有高级拖拽操作，但必须保证可以查看作品、发送消息和选择 Panel。

## 13. 技术与交付约束

- 交付可直接运行的前端原型，不只交付设计说明或静态图片。
- 使用本地演示数据，不接真实 API。
- 演示状态必须是确定性的，刷新后可回到初始状态。
- 不引入无限画布或重型流程图库。
- 如果在 DoodleStory 仓库中实现，优先沿用 React、TypeScript 和现有构建方式。
- 不要求复用当前 `main.tsx` 的任务详情结构；原型可以使用独立路由和组件。
- 不修改现有任务页面，不把原型伪装成已经接通后端的正式功能。
- 不生成 Mock 业务结果用于正式产品；本次本地原型中的演示数据必须明确标注为`设计演示`。

## 14. 评审标准

评审时优先观察以下问题：

1. 进入页面三秒内，是否知道这是哪个作品、Agent 在做什么、哪张图被选中？
2. 漫画图片是否真正成为视觉中心？
3. 是否能在两次操作内完成“选中第三张并提出修改”？
4. 对话、画布和检查器是否像同一个系统，而不是三个拼在一起的页面？
5. Agent 的行动是否可理解，但没有暴露噪声和隐藏思维？
6. 多个图片版本是否容易比较，当前版本是否明确？
7. 运行状态变化是否稳定，不会让布局不断跳动？
8. 页面是否克制、有创作感，而不是通用管理后台？
9. 如果移除阴影和装饰，信息层级是否仍然成立？
10. 这个界面是否让用户愿意长时间停留并持续修改作品？

## 15. 非目标

本次前端原型不需要设计：

- Agent 后端实现。
- 真实模型调用。
- 计费和积分结算。
- 完整项目列表。
- 管理员页面。
- 风格库和角色库的完整 CRUD。
- 视频剪辑时间线。
- 多人协作。
- 无限画布。
- 生产环境异常恢复。

这些能力不应干扰本次对“Agent 对话 + 分镜画布 + 对象检查器”核心体验的判断。
